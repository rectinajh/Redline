## 一、问题定义

加密钱包通常会解释一笔交易可能对资产做什么，但很少检查这笔交易是否符合交易者自己制定的规则。当某个代币快速上涨时，用户可能忽略通用警告、扩大仓位、放宽滑点，或者在几分钟前已经放弃原计划后仍然继续交易。

Redline 是一个交易前决策护栏和交易后证明系统。用户在 swap 前定义一组个人限制；交易完成后，Flare 验证外部交易，并生成公开的 `LINE HELD` 或 `LINE CROSSED` 结果。

Redline 不是价格预测机器人、自动交易员或普通钱包模拟器。它的产品承诺是行为层面的：在情绪最强之前，让用户明确自己的边界；交易之后，让用户能验证自己是否遵守了边界。

## 二、产品为什么让人记住

Redline 是一个带有明显后果的交易仪式：

1. 用户画出红线：交易对、最大仓位、最大滑点、有效期。
2. 用户签署 Redline Receipt。
3. 用户自己执行交易。
4. Flare 作为外部裁判，输出 `LINE HELD` 或 `LINE CROSSED`。

视觉上不要做成 Dashboard，而要像一个高对比度的交易检查点：一条红线、一个决定、一个裁决。

## 三、硬约束

- Flare Summer Signal 截止时间：2026-08-14 19:59，剩余时间约一天。
- 首选目标：Bounty 1，Interoperable Asset Products。
- 部署网络：Coston2，Chain ID 114。
- 只保留一个核心机制：交易前承诺规则，交易后由 Flare 验证是否守约。
- 只支持一个 EVM 测试环境、一个 router、一个 token pair 和一笔 demo 交易。
- 在确认具体 FDC 交易源之前，不承诺支持任意链。
- 不做生产级投资建议、自动交易、资金托管或防止亏损的保证。
- AI 可以把自然语言转成候选规则，但不能成为最终裁判。
- Moss 可以展示确定性的模拟结果，但模拟结果不是信任根。

## 四、已确认的产品前提

1. 对当前原型来说，冲动交易和违反自身规则，比泛泛的价格预测更值得解决。
2. 唯一核心机制是：`画红线 → 完成交易 → 让 Flare 裁判`。
3. Flare 必须验证外部交易或与交易绑定的加密事实。前端布尔值或普通服务器数据库不够。
4. FDC 是 Bounty 1 的首选原语，因为它可以 attestation 外部交易数据，并让 Flare 合约在验证 proof 后生成结果。
5. 第一版是交易纪律证明，不是强制阻止交易。用户仍然由自己的钱包签署 swap，Redline 只记录用户是否遵守规则。
6. 在截止时间前，一个完整的单路径 demo 比一个半成品的多链风险平台更有价值。

## 五、借鉴获奖钱包项目的模式

之前的获奖钱包项目说明了一种值得借鉴的信任姿态：解释、提醒、模拟，但绝不越权。Redline 应该借鉴这种姿态，同时保留自己的核心机制。

用户签名前，Redline 展示一张有优先级的 **Redline Brief**，包含四类证据：

1. **风险优先级**：例如 `仓位过大`、`滑点超过红线`、`授权扩大钱包暴露面`。
2. **模拟结果**：预计资产变化、预计输出、价格影响和授权变化，由 Moss 或确定性模拟器提供。
3. **数据来源**：每个事实都标注来源，例如 `FTSO reference`、`Local simulation`、`Wallet state`、`FDC-verified transaction`。
4. **签名边界**：明确告诉用户：`Redline cannot sign or execute this trade. Your wallet remains in control.`

这样，产品在交易前就有实际价值；而 FDC 证明的 Receipt 仍然是交易后的 Flare 核心机制。界面不能暗示 AI 分数是安全保证，也不能暗示 Redline 能保证用户不亏损。

前一个项目的 localhost 入口和 mock fallback 是本次提交必须避免的风险。Redline 必须发布可访问的公网前端、准确的合约地址、真实 Coston2 explorer 链接；如果使用 fixture，界面必须明确标记为 `Demo data`。Mock 可以帮助支持 UI，但不能伪装成 Flare proof。

## 六、竞品和市场位置

现有交易模拟器主要关注：

- 资产会如何变化
- 授权会如何变化
- Gas 和滑点
- 合约行为
- 可疑 dApp 或危险交互

钱包策略系统主要关注：

- 钱包允许支出多少
- 哪些资产可以发送
- 哪些地址或合约被允许交互
- 单笔或周期性支出限制

行为交易工具主要关注：

- 冷静期
- 每日亏损限制
- 交易次数
- 交易日志
- 事后复盘

Redline 的差异化位置是一个可携带、可验证的交易纪律 Receipt：

> 我之前对自己承诺了什么？外部链上的事实能不能证明我守住了它？

这也是选择 Flare 的产品理由。Flare 合约不是简单保存用户自述的日志，而是验证外部交易 proof，并计算确定性的守约结果。

## 七、方案比较

### 方案 A：Redline Receipt

**概念**：用户在交易前提交三条限制，执行一笔外部 EVM swap，提交 FDC proof，Flare 在 Coston2 上写入 `LINE HELD` 或 `LINE CROSSED`。

**核心机制**：

> Draw the line. Make the trade. Let Flare judge.

**开发工作量**：S
**风险**：中
**目标 bounty**：Bounty 1

**优点**：

- 最小但完整的 Flare 故事。
- 可以复用之前 ProofPay 对 attestation、proof verification、replay protection 和 explorer 状态的判断。
- 用户和评审在 10 秒内就能理解机制。

**缺点**：

- 必须立即确认选定的外部 EVM 交易源和 demo swap 能否通过 FDC 验证。
- 必须把 demo 限定在一条支持的链、一个 router、一个交易对和一个 fixture 交易。

### 方案 B：Redline Vault

**概念**：用户把 demo 资金或测试资产放入 Flare vault。只有当外部交易被证明没有越过红线后，vault 才允许结算或释放资金。

**核心机制**：

> Flare 不只记录你的边界，还控制越线之后会发生什么。

**开发工作量**：L
**风险**：高
**目标 bounty**：Bounty 1

**优点**：

- Flare 控制一个可见的资金后果，不只是生成 Receipt。
- 未来可以扩展为冷静期 vault、交易保险和自我约束账户。

**缺点**：

- 在一天内增加资金托管、释放、超时和跨链执行复杂度。
- 容易被评审理解成普通 escrow 或智能钱包 demo。

### 方案 C：Redline Black Box

**概念**：用户加密自己的真实限制，让 FCC TEE 只返回签名后的 `held/crossed` 结果，不公开规则本身。

**核心机制**：

> Private limits. Public verdict.

**开发工作量**：XL
**风险**：很高
**目标 bounty**：Bounty 2

**优点**：

- 隐私直接改变产品体验：别人能验证结果，却看不到用户的真实风险边界。
- 如果完整跑通，与 Confidential Compute bounty 的匹配度最高。

**缺点**：

- 需要 FCC extension、proxy、Docker 服务、HTTPS tunnel、加密 payload 和签名验证。
- 同时处理 FCC、外部交易 proof 和链上结算，极易变成半成品。

## 八、推荐方案

选择 **方案 A：Redline Receipt**，参加 **Bounty 1：Interoperable Asset Products**。

Flare-native 核心机制是：

> 用户在 swap 前签署交易限制；交易发生后，Flare 验证真实的外部交易，并给出最终裁决。

Redline 不应该声称能阻止所有坏交易。它在签名前增加摩擦，在交易后增加可验证的责任。Demo 必须展示两种结果：

- 合规交易：`LINE HELD`
- 超过仓位或滑点的交易：`LINE CROSSED`

展示失败路径很重要。它能证明合约是在比较真实事实，而不是把预写好的成功页面展示出来。

## 九、MVP 数据模型

```text
RedlineReceipt {
  trader: address
  chainId: uint256
  router: address
  tokenIn: address
  tokenOut: address
  maxInput: uint256
  minOutput: uint256
  maxPositionBps: uint256
  expiry: uint256
  simulationHash: bytes32
  nonce: bytes32
}
```

合约应保存 hash 或 commitment，而不是不必要的个人文本。Proof adapter 只验证当前 demo 所需的外部交易字段，并拒绝被重复使用的 Receipt 或不匹配的交易。

## 十、MVP 用户界面

### 1. Before：交易前

标题：`Draw your redline.`

展示：交易对、最大仓位、最大滑点、有效期，以及唯一主按钮 `DRAW MY REDLINE`。

### 2. Brief：风险摘要

只用一屏展示：

- 最大风险
- 模拟的资产变化
- 价格影响
- 授权变化
- 每项数据的来源
- 用户自己签名、Redline 不代签的边界

### 3. During：交易中

标题：`Your line is set.`

展示 Receipt hash、链、router 和执行交易的链接。Redline 不执行交易。

### 4. After：交易后

展示用户承诺的限制、真实交易数值、FDC proof 状态，以及一个大结果：

- `LINE HELD`
- `LINE CROSSED`

## 十一、Demo 语言

主宣传语：

> The market wants you emotional. Redline makes you choose your limits first.

产品解释：

> We do not predict the market or trade for you. We prove whether you kept your own rules.

中文表达：

> 市场想让你冲动，Redline 让你先选择自己的边界。

> 我们不预测市场，也不替你交易。我们证明你有没有遵守自己的规则。

## 十二、开放问题

- 当前 Coston2 的 FDC 配置支持哪个外部 EVM 交易源和 router？
- 团队能否在提交前制作一笔真实合规交易和一笔故意越线的 fixture？
- FDC proof response 是否包含验证金额、router、交易对和实际输出所需的字段？
- `maxPositionBps` 应相对于交易前钱包余额计算，还是为了赶工使用固定绝对金额？
- 如果 FDC finalization 超过录制视频的时间，是否可以从已 finalized 的 proof 开始，同时展示真实 request 和交易路径？

## 十三、成功标准

1. 观众在前 10 秒能解释核心机制。
2. Demo 展示真实的交易前 Receipt、真实外部交易、FDC proof 状态和 Flare 裁决。
3. 签名前页面标注风险优先级、数据来源、模拟结果和签名边界。
4. Redline 永远不请求私钥、不替用户签名，也不声称警告能保证安全。
5. 合约拒绝过期 Receipt、不匹配的 router 或交易对、超过限制的金额/输出以及重复 proof。
6. 视频展示 `LINE HELD` 和 `LINE CROSSED` 两种结果。
7. README 包含 Coston2 Chain ID、RPC、部署地址、proof retrieval 步骤、已知限制和复现命令。
8. 提交页能够填写项目名、bounty、产品简介、目标用户、demo/video/app 链接、GitHub、Flare 用法、本次新做内容、合约地址和 roadmap。

## 十四、发布计划

以一个公开 Web demo 和 GitHub 仓库交付。前端可以使用静态部署或简单的 Next.js/Vite 部署。

仓库必须包含：

- 合约
- 部署脚本
- proof fixture/request 脚本
- 前端
- ABI
- README

黑客松阶段可以手动部署，但必须写清楚步骤。黑客松之后再增加 GitHub Actions，用于运行合约测试和自动发布前端。当前不需要 npm 包、桌面应用或原生移动端分发。

## 十五、依赖项

- 已充值的 Coston2 钱包和 RPC。

## 十六、下一步

1. 先确认确切的 FDC EVM transaction attestation 路径和目标 fixture。失败后立即换支持的交易源，不要继续扩展 Redline。
2. 根据目标链定义最小 Receipt 字段，并为 held、crossed、expired、mismatched、replayed 编写合约测试。
3. 把 Receipt 合约部署到 Coston2，准备一笔已知合规 fixture 和一笔已知越线 fixture。
4. 构建一屏 Redline Brief：风险优先级、模拟结果、数据来源和明确签名边界。
5. 构建结果页，使用 Redline 的语言，不要做成 Dashboard。
6. 在录视频前发布公网前端、GitHub、合约地址和 fixture 链接。
7. 录制 60–90 秒视频：红线、Brief、交易、proof、held、crossed、explorer。
8. 完成提交材料，删除所有 `TBD` 地址或链接。

## 十七、唯一现实作业

在制作更多 UI 之前，先证明这个单一高风险假设：

> 一笔选定的外部 EVM swap 能产生一份 FDC 可验证的交易 proof，并且 proof 字段足以让 Coston2 合约计算 `LINE HELD` 或 `LINE CROSSED`。

冻结这笔交易作为 demo fixture。然后只围绕它制作一屏 Redline Brief、Receipt 和最终裁决。录视频前必须发布 app 和 proof 链接。

- **项目名**：Redline
- **Bounty**：Bounty 1 — Interoperable Asset Products
- **产品简介**：Redline 让交易者在 swap 前设定自己的限制，再使用 Flare 验证真实交易是否守住这些限制。
- **目标用户**：进行高波动 token swap、容易追涨或临时扩大仓位的个人交易者。

- **本次新做了什么**：Redline Receipt、规则 commitment、风险 Brief、simulation/source labels、FDC proof adapter、held/crossed verdict 和 replay protection。
- **合约地址**：部署后填写 Redline Receipt 合约、FDC verification/registry 地址和相关 token/router 地址，不能留 `TBD`。
- **短期 roadmap**：扩展 BTC/DOGE/XRP/FAssets 场景；支持更多 EVM 链；将私密风险规则接入 FCC；探索 Redline Vault 和冷静期资金。

## 十九、我观察到的思考方式

- 你拒绝了听起来像合规软件的名字，坚持要有“性感”的产品表达，这暴露出产品真正的能量：危险、诱惑和一条看得见的边界。
- 你没有接受第一个技术上安全但产品感弱的建议，而是保留核心机制，同时要求它成为用户会记住的产品。
- 你把冲动交易定义为一个“刚的需求”，这比泛泛的加密安全或 AI 交易建议更有力量。
- 在比较高上限的 Vault 和更戏剧化但更危险的 FCC Black Box 后，你选择了最小完整路线，把野心放在故事里，把风险限制在范围里。

## Problem Statement

Crypto wallets explain what a transaction may do, but they rarely ask whether the transaction follows the trader's own rules. When a token is moving fast, the user can ignore generic warnings, increase size, widen slippage, or enter after abandoning the plan they had five minutes earlier.

Redline is a pre-trade decision guardrail and post-trade proof. Before a swap, the user defines a small set of personal limits. After the swap, Flare verifies the external transaction and produces a public `LINE HELD` or `LINE CROSSED` verdict.

Redline is not a price-prediction bot, an autonomous trader, or a generic wallet simulator. Its product promise is behavioral: make the user's own limit explicit before the emotional moment, then make adherence verifiable afterward.

## What Makes This Cool

The interaction is a small ritual with a visible consequence:

1. The user draws a redline: pair, maximum position, maximum slippage, expiry.
2. The user signs the Redline Receipt.
3. The user executes the trade.
4. Flare acts as the external judge and says `LINE HELD` or `LINE CROSSED`.

The visual language is not a dashboard. It is a high-contrast trading checkpoint: one red line, one decision, one verdict. The rough wireframe is at `/tmp/gstack-redline-wireframe.html`; it was not rendered because the gstack browse binary is not installed in this environment.

## Premises

1. Impulsive trading and rule-breaking are a sharper product problem than generic price prediction for this prototype.
2. The unique mechanic is `Draw a redline → make the trade → Flare judges the receipt`.
3. Flare must verify the external transaction or a cryptographically bound transaction fact. A front-end boolean or server database is not sufficient.
4. FDC is the preferred Bounty 1 primitive because it can attest external transaction data and let a Flare contract verify a proof before producing the verdict.
5. The first release is a proof of discipline, not a hard block. The user's wallet still signs the swap; Redline records whether the user kept the rules.
6. A complete single-path demo scores better than a half-built multi-chain risk platform.

## Landscape Synthesis

Existing transaction simulators focus on asset movements, approvals, gas, slippage, contract behavior, and suspicious interactions. Wallet policy systems focus on programmable spending limits and authorization scope. Behavioral trading tools focus on cooldowns, daily loss limits, trade counts, journals, and post-session analysis.

Redline's distinct position is the portable behavioral receipt: `What did I promise myself, and did the external chain prove that I kept it?` This is the product-level reason to use Flare. The Flare contract is not merely storing a self-reported journal entry; it verifies an external transaction proof and computes a deterministic verdict.

## Borrowed Winning Pattern

The prior winning wallet project suggests a useful trust posture: explain, remind, simulate, and never overreach. Redline should borrow that posture while keeping its own mechanic.

Before the user signs, Redline presents a prioritized **Redline Brief** with four evidence blocks:

1. **Risk priority**: `Oversized position`, `Slippage above your line`, or `Approval expands wallet exposure`.
2. **Simulation**: expected token movement, estimated output, price impact, and approval delta from Moss or the deterministic simulator.
3. **Data source**: label each fact as `FTSO reference`, `local simulation`, `wallet state`, or `FDC-verified transaction`.
4. **Signing boundary**: `Redline cannot sign or execute this trade. Your wallet remains in control.`

This makes the product useful before the transaction, while the FDC-backed receipt remains the unique Flare mechanic after the transaction. The interface must never imply that an AI score is a guarantee or that Redline prevented a loss.

The prior project's localhost entry point and mock fallbacks are a warning for this submission. Redline must publish a reachable frontend, exact contract addresses, a real Coston2 explorer link, and a visible `Demo data` label whenever a fixture is used. A mock may support the UI, but it cannot be presented as a Flare proof.

## Approaches Considered

### Approach A: Redline Receipt

**Summary:** Commit three limits before a swap, execute one external EVM transaction, submit an FDC proof, and write `LINE HELD` or `LINE CROSSED` on Coston2.

**Effort:** S
**Risk:** Medium
**Target:** Bounty 1

**Pros:**

- Smallest complete path with a strong Flare story.
- Reuses the prior ProofPay reasoning around attestation, proof verification, replay protection, and explorer-verifiable state.
- The user and reviewer can understand the mechanic in under 10 seconds.

**Cons:**

- Requires immediate confirmation that the selected external EVM transaction source and demo swap can be attested through FDC.
- Must constrain the demo to one supported chain, router, pair, and fixture transaction.

### Approach B: Redline Vault

**Summary:** Hold demo funds in a Flare vault and release or settle them only after the external trade is proven to respect the redline.

**Effort:** L
**Risk:** High
**Target:** Bounty 1

**Pros:**

- Flare controls a visible financial consequence, not just a receipt.
- Provides a natural long-term path to cooling-off vaults, trade insurance, and self-enforced accounts.

**Cons:**

- Adds custody, release, timeout, and cross-chain execution complexity under a one-day deadline.
- Risks being perceived as a generic escrow or smart-wallet demo.

### Approach C: Redline Black Box

**Summary:** Encrypt the user's true limits and let an FCC TEE return only a signed `held/crossed` verdict.

**Effort:** XL
**Risk:** Very high
**Target:** Bounty 2

**Pros:**

- Privacy directly changes the experience: observers can verify the result without seeing the user's risk limits.
- Strongest conceptual fit for Confidential Compute if the full TEE flow is already available.

**Cons:**

- Requires the FCC extension, proxy, Docker services, HTTPS tunnel, encrypted payload path, and signed result verification.
- Combining FCC setup with external transaction proof makes a complete demo unlikely in the remaining time.

## Recommended Approach

Choose **Approach A: Redline Receipt** for **Bounty 1 — Interoperable Asset Products**.

The Flare-native mechanic is:

> A user commits to a trading limit before the swap; Flare verifies the real external transaction and issues the verdict.

The product should not claim to stop every bad trade. It creates friction before signing and accountability after execution. The demo should intentionally show both outcomes:

- A compliant trade: `LINE HELD`.
- An over-sized or over-slippage trade: `LINE CROSSED`.

Showing the failure path proves that the contract is comparing facts rather than displaying a prewritten success screen.

### MVP data model

```text
RedlineReceipt {
  trader: address
  chainId: uint256
  router: address
  tokenIn: address
  tokenOut: address
  maxInput: uint256
  minOutput: uint256
  maxPositionBps: uint256
  expiry: uint256
  simulationHash: bytes32
  nonce: bytes32
}
```

The contract should store a hash/commitment rather than unnecessary raw personal text. The proof adapter should verify the external transaction fields needed for the selected demo and reject a reused receipt or mismatched transaction.

### MVP UI states

1. **Before**: `Draw your redline.` Show pair, max position, max slippage, expiry, and a single `DRAW MY REDLINE` button.
2. **Brief**: Prioritize the biggest risk, show simulation and source labels, then state the signing boundary before the wallet prompt.
3. **During**: `Your line is set.` Show receipt hash, chain, router, and a link to execute the swap. Redline does not execute it.
4. **After**: Show committed limits, actual transaction values, FDC proof status, and one large verdict: `LINE HELD` or `LINE CROSSED`.

### Demo language

> The market wants you emotional. Redline makes you choose your limits first.

> We do not predict the market or trade for you. We prove whether you kept your own rules.

## Success Criteria

1. A new viewer can explain the mechanic after watching the first 10 seconds.
2. The demo shows a real pre-trade receipt, a real external transaction, an FDC proof state, and a Flare verdict.
3. The pre-sign screen labels data sources, simulation output, and the exact signing boundary.
4. Redline never requests a private key, never signs on behalf of the user, and never claims that a warning guarantees safety.
5. The contract rejects an expired receipt, mismatched router or pair, over-limit amount/output, and replayed proof.
6. The video shows both `LINE HELD` and `LINE CROSSED`.
7. The README contains the Coston2 chain ID, RPC, deployment addresses, proof retrieval steps, known limitations, and one-command reproduction instructions.
8. The submission page can answer: project name, bounty, product summary, target user, demo/video/app links, GitHub link, Flare usage, new work, contract addresses, and roadmap.

## Distribution Plan

Ship as a public web demo with a GitHub repository. The hosted frontend can use a static deployment or a simple Next.js/Vite deployment. The repository must contain the contracts, deployment scripts, proof fixture/request script, frontend, ABI, and README.

For the hackathon, deployment is manual and documented. A post-hackathon GitHub Actions workflow can run contract tests and publish the frontend on merge. No package manager or native app distribution is required for this deliverable.
